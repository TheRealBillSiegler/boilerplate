    ADR-002: Depend on Copier's internal Template/Worker via a single audited shim

    Status: Accepted

    Context

    Copier does not expose Template or Worker in its public API (copier.__all__ is load_settings, run_copy, run_recopy, run_update, Phase, Settings, VcsRef). Boilerplate's composition engine is built on these internal classes: MergedTemplate subclasses Template to present a consolidated question schema, and every layer's render, at compose and at update, runs through a Worker subclass that exposes the layer's scoped view, the consolidated schema of the layer and its ancestors (design 04 §Scoped view), rather than through Copier's public run_copy/run_update. These are private symbols Copier may relocate without a deprecation cycle.

    Decision

    Funnel all coupling to Copier internals through one module, src/boilerplate/integrations/copier_types.py, importing from the modules where Copier actually defines them (copier._main.Worker, copier._template.Template), and pin Copier to a tested range (copier>=9.15,<10 in pyproject.toml). A relocation of these symbols then breaks one file, loudly, via the guard test (tests/boilerplate/integrations/test_copier_types.py) during CI rather than at render time for a user.

    Compose and update share one way in. Both hand Copier each layer's scoped view through the same Worker subclass, built on the Worker that copier_types.py imports. Compose renders every layer through it, boilerplate update runs Copier's update once per layer through it, and every use of Copier internals on either path MUST go through the shim.

    The scoped views live in fields of a Worker subclass, two per update step, and the subclass's template property builds template from the view in those fields that matches the render Copier is making, together with the src_path: the scoped view joined from the recorded versions of the layer and its ancestors for the old copy, which renders the layer's recorded source at its recorded _commit, and the scoped view joined from their target versions for the in-place render and the new copy. The property tells the old copy from the other two renders by the render's destination, not by vcs_ref, because the three renders can carry one ref when only an ancestor moves; the name prefixes it reads are listed under Audited internals, and the in-place render's destination is the project. Copier's update builds its three renders (the old copy, the in-place render and the new copy) with dataclasses.replace, which constructs each new worker from dataclass fields. A template set on one worker instance reaches none of the three renders; replace copies a view held in fields into all of them.

    Audited internals (read at Copier 9.18.1). The shim and its guard test MUST cover each Copier internal Boilerplate depends on: copier._main.Worker and copier._template.Template; Worker._apply_update's construction of its three renders with dataclasses.replace; the copier._main.old_copy. and copier._main.new_copy. temporary-directory name prefixes (the prefix arguments of those two TemporaryDirectory calls), which the template property reads to tell the old copy from the other renders; the vcs_ref the old copy (the subproject template's commit) and the new copy (resolved_vcs_ref) carry, which is why the property cannot select a view by ref; and the private copier._main._operation ContextVar, which the post-walk task run sets to "update" because only run_copy, run_recopy and run_update set it (the as_operation decorator) and Copier's task runner reads it (in Worker._execute_tasks). The post-walk task run also enters Copier's tasks phase (copier._types.Phase.TASKS, the phase Worker.run_copy sets with Phase.use around Copier's own task run), so a task's when: sees _copier_phase == "tasks" as it does under Copier. The Worker subclass also overrides and calls Worker._ask, which compose's questionnaire pass calls to ask the full merged schema once without rendering, since Copier has no public call that only asks. It calls Worker._execute_tasks for the post-walk task run, and Worker._render_context and Worker._external_data for the rejected-answer check, which validates a recorded answer through copier._user_data.AnswersMap and Question as _ask does. A template Copier never builds itself registers its cleanup through Worker._cleanup_hooks and Template._cleanup, because rendering a VCS template clones it into a temporary directory that only _cleanup removes.

    A relocation of Worker or Template inside Copier breaks compose and update in copier_types.py alone, where the guard test reports it, and the copier>=9.15,<10 pin bounds the Copier versions both paths run on. A test MUST drive one per-layer update through the subclass, since a symbol check does not see the dataclasses.replace contract the update walk depends on.

    Options considered

    • Scattered from copier import … across the codebase — every upgrade break surfaces in many files, and the top-level import path emits a deprecation warning.
    • Reimplement Copier's render/merge — large, duplicates Copier, contradicts ADR-001.
    • Vendor/fork Copier — maintenance burden out of proportion to the need.
    • Single audited import shim + version pin (chosen) — one change point on upgrade; the deep _main/_template paths avoid the deprecation warning.
    • Selecting the view by vcs_ref — rejected: when only an ancestor moves, the old copy, the new copy and the in-place render carry one ref and need different views.
    • A merged template set on one worker instance — rejected: dataclasses.replace rebuilds the update renders without it (Verification (2026-09-30)).

    Consequences

    • One file changes when Copier relocates these symbols; the import stays warning-free; ruff + pyright-strict clean.
    • Coupled to a private API: every Copier upgrade must be re-validated against the shim's guard test and the per-layer update test.
    • The >=9.15 floor is pragmatic, not a verification gap: 9.15 is the version in use and tested, and we deliberately do not support or look further back (possibly ever). The <10 cap forces re-validation at Copier's next major.
    • Re-architecture: this decision stands until the Copier integration is re-architected (e.g., adopting the evaluated file-based merged-template approach); this ADR is then rewritten in place.

    Verification (2026-06-09)

    copier_types.py is the only site importing Copier internals (grep); MergedTemplate subclasses the shim's Template (composition/rendering/models/merged_template.py:14); the guard test is present.

    Verification (2026-09-30)

    Empirical run against the bundled project and streamlit templates (Copier 9.18.1, Windows, local git clones, --defaults, skip_tasks): both layers cloned into tagged git repositories, a project composed by boilerplate new and rehomed to the clones. Each new tag edited the README line that renders project_name and appended a file rendering seven inherited answers; a user line appended to the README before the first update had to survive.

    Mechanism Orders Result
    A Worker subclass holding the merged questions and the extension union in fields, template built from them; Worker.run_update() called on the subclass instance per layer with the union of the per-layer answers files as data (the merge order of the union was not recorded) project then streamlit, and streamlit then project; v2 then v3 All 8 updates exit 0, with no conflict markers, no .rej files and no unmerged paths; the five inherited answers that Copier records persist in streamlit's answers file after every update; the two derived values render (widget_co, widget-co); the package directory and the user line survive
    worker.template set to the merged template on one instance Both orders The first streamlit update exits 0 but its answers file loses the five inherited answers and the derived values render empty; the second update pauses with conflict markers in README.md and the probe file

    Verification (2026-10-06)

    Empirical run against the bundled project and streamlit templates (Copier 9.18.1, Windows, git 2.55, one tagged git repository per layer, project and streamlit composed at v4 under their scoped views): project v5 removed a question its v4 files rendered, and project was updated v4 to v5 through a Worker subclass holding one scoped view per ref. The old copy rendered under the v4 view with the value recorded in project's answers file, also in a control run that passed no data at all, and the update finished with no conflict markers, no .rej files and no unmerged paths; the answers file then dropped the removed question. The per-layer views, their answers files and their extensions are recorded in ADR-015 §Verification (2026-10-06).

    Relationship to other ADRs

    • ADR-001 records the decision to adopt Copier. This ADR records the mechanism of that integration: Boilerplate depends on Copier's internal Worker and Template through the shim. A file-based merged-template approach that would avoid the internal dependency was evaluated and not adopted.
    • ADR-015 — the update walk this shim serves: every render of every layer's update sees the layer's scoped view at the versions it renders.
