    ADR-017: Build backend — uv_build by default, hatchling by choice

    Status: Accepted

    Scope note. This ADR fixes which build backends the project template offers, which one it renders by default, how the uv_build version bound stays current, and how an existing project keeps its backend through copier update. For what exists today, see status.md.

    Context

    The project template renders a pure-Python package with a static version and one src/<package_name> directory, and its toolchain is built on uv (dev-environment landscape). The streamlit template extends project, so it renders the same [build-system] table. The build backend is the one slot of that toolchain that the mapping table leaves unfilled, and Boilerplate's rule for slots is one opinionated pick each, with a named override.

    Projects rendered before this decision declare hatchling with no version bound. Three facts bear on the pick:

    • uv ships its own backend. uv_build is the backend that plain uv init declares since uv 0.12.0, and uv's documentation calls it "a great choice for most Python projects" (uv build backend). It builds pure Python only.
    • uv's own docs name the escape hatch. The documentation advises that "when build scripts or a more flexible project layout are required, consider using the hatchling build backend instead" (uv build backend). hatchling runs build hooks and plugins, reads the version from git tags through hatch-vcs, and selects files with its own configuration.
    • A backend cap needs upkeep. uv bumps its minor version for breaking changes and its patch version for everything else (uv versioning policy), and its documentation tells uv_build users to cap the requirement at the next minor. uv released 0.12.0 on 2026-07-28 and 0.13.0 on 2026-10-09, so a cap of that kind needs a bump every few months.

    A render that picks a backend also decides what happens when copier update meets a project rendered earlier. A new question with a default is applied silently by copier update --defaults, so adding the question without a migration moves every existing hatchling project to uv_build. That move drops any [tool.hatch] configuration and any dynamic = ["version"] entry the project relies on, and narrows the sdist from every file git does not ignore to the package and its metadata. Versioning § What qualifies as breaking classes "changing the default value of an option incompatibly" as breaking.

    Decision

    The project template MUST ask a build_backend question with two choices, uv_build (the default) and hatchling, and MUST render the [build-system] table, plus the [tool.hatch] table for hatchling, from that answer. The streamlit template inherits the question from project and does not redeclare it.

    1. The question. build_backend is a str question with choices, placed before package_index_url in the project template's copier.yml. Its choices are the two backend names, with no description on either; the project template guide says when to pick each.
    2. The uv_build render. The template renders requires = ["uv_build>=0.13,<0.14"] and build-backend = "uv_build", with no [tool.hatch] table. uv_build finds src/<package_name> without configuration.
    3. The hatchling render. The template renders requires = ["hatchling>=1.27"], build-backend = "hatchling.build" and the [tool.hatch.build.targets.wheel] table with packages = ["src/<package_name>"]. Hatchling 1.27.0 is the first release that writes the PEP 639 license fields (License-Expression, License-File) by default; 1.26.x writes the old License: field. The requirement has no cap, the same as hatch new writes it.
    4. The bound is a minor range. The uv_build requirement takes the current uv minor as its floor (>=0.13, not >=0.13.3), so every uv 0.13.x runs its bundled copy of the backend and fetches nothing from a package index. A private package_index_url therefore mirrors no build backend for a project inside the range.
    5. The bound moves with the Docker tag. The streamlit template's Dockerfile installs uv from the image tag ghcr.io/astral-sh/uv:<minor>. For every uv minor, the uv_build range and that tag move together in one change, and a test renders streamlit and asserts that the range's minor equals the tag's minor. An image older than the range's floor fetches uv-build from the package index and fails offline with a cold cache, which is the reason for the pairing. The test catches drift between the two values and does not catch staleness, so the release checklist in RELEASING.md names the uv minor, and uv's own warning (point 6) tells a user that a generated project's cap is stale.
    6. uv's behavior outside the range. uv uses its bundled backend only when requires is a single uv_build entry whose range contains uv's version. A uv newer than the cap (0.13.3 against <0.13) builds with its bundled copy and warns on every uv sync and uv build. A uv older than the floor fetches uv-build from the index, as the documentation describes. The documentation's statement that an out-of-range uv "uses a compatible version of the uv_build package" describes only the second case.
    7. A before migration keeps existing projects on hatchling. The project template's copier.yml declares its first _migrations entry with when: "{{ _stage == 'before' }}" and no version gate: bundled layers share the repository's tag stream, so a gate at the version that introduces the question would skip a project rendered at the tag just before it, and the key check below makes the entry a no-op once the answer exists. The migration runs the update's Python ({{ _copier_python }}) to append build_backend: hatchling to the layer's answers file (.copier-answers.project.yml, passed to the script as {{ _copier_conf.answers_file }}) when that file exists and holds no build_backend key. copier update --defaults then keeps a project rendered before the question existed on hatchling, and an explicit --data build_backend=hatchling keeps it as well. A project that has a build_backend answer is untouched.
    8. Switching is a re-answer. A project that changes backend after generation re-answers the question with copier update --data build_backend=<choice>, which re-renders the [build-system] table and the [tool.hatch] table together.

    When to choose which backend

    The table covers the nine backends a Python project most often meets; the two the template offers come first. It leaves out whey, which had four sdists in the Quansight Labs sample, py-build-cmake, which has about 31 thousand downloads a month, and enscons, which has about 10 thousand downloads a month and little activity. A backend outside the first two is a hand edit of [build-system] in the generated project, and the template scaffolds no Cargo.toml or CMakeLists.txt for the compiled rows.

    Backend Choose it when Avoid it when Notes: PEP 639, editable installs, version bounds
    uv_build (default) Pure Python; static version; one src/<package>; uv toolchain Version from git tags; build hooks; generated files that git ignores inside the package; several top-level packages PEP 639 output. PEP 660 editable hook. Bound >=0.13,<0.14; uv's documentation caps at the next minor
    hatchling Build hooks; version from git (hatch-vcs); custom file selection; plugins A build that must fetch no build requirement (uv_build runs from uv's bundled copy); native extensions without a custom hook PEP 639 output by default from 1.27.0 (1.26.x writes the old License: field). Editable installs through a .pth file. Floor >=1.27, no cap
    setuptools Existing setup.py or cmdclass; small C extension through ext_modules; setuptools-rust New pure-Python project; non-.py data without package-data (the wheel silently omits it) PEP 639 from 77.0.1, the first release on PyPI (77.0.0 was never published); the PyPA tutorial uses >=77.0.3. Editable installs from 64.0.0; a binary extension is a snapshot
    flit-core Tiny module; __version__ as the version; nothing else Hooks; git versioning; generated files PEP 639 from 3.11. Flit's documentation: >=3.11,<5; the PyPA tutorial tab: >=3.12.0,<5
    pdm-backend The team runs PDM; built-in SCM version A uv-run project, where PDM's workflow owns the lock PEP 639 from 2.4.0. Editable installs through path or editables. PyPA tutorial: >=2.4.0
    poetry-core The team runs Poetry; no extension modules A uv-run project; extension modules (Poetry calls its build scripts "still considered unstable") [project] table from 2.0.0; PEP 639 from 2.2.0. Poetry's documentation: >=2.0.0,<3.0.0
    maturin Rust through PyO3, cffi or uniffi Code with no Rust PEP 639 in full from 1.9.0 and the License-Expression fix in 1.9.2. A Rust edit needs a rebuild. uv init scaffolds it and writes cache-keys
    scikit-build-core C, C++, Fortran or Cython with CMake, pybind11 or nanobind A codebase with no CMake PEP 639 from 0.11.0. Editable redirect; rebuild-on-import is experimental. uv init --build-backend scikit scaffolds it
    meson-python A Meson codebase; the numerics stack (numpy and scipy build with it) A project that wants uv init scaffolding or automatic cache-keys PEP 639 from 0.18.0. Editable rebuild-on-import needs --no-build-isolation. uv init rejects it

    Options considered

    • uv_build default, hatchling by choice (chosen). The default covers the template's shape (pure Python, static version, one src/<package_name>) and is the backend uv itself scaffolds. hatchling is the one other backend that does a job uv_build does not for this template: hooks, plugins, and a version from git. Each of the two has a stated trigger in the question's help strings.
    • hatchling as the default (the runner-up). The PyPA packaging tutorial states "this tutorial uses Hatchling by default" (packaging projects), and the Scientific Python Development Guide says "If you don't have an existing preference, hatchling is an excellent choice" (packaging simple). hatchling needs no cap upkeep. PyPI recorded about 320 million hatchling downloads and about 15 million uv-build downloads in the month before 2026-10-19 (pypistats); pip build isolation and CI inflate both counts, so they are not adoption shares. Rejected: the template's toolchain is uv, uv recommends uv_build for this project shape, and the cap has cost only bumps so far, because each uv release note states "no breaking changes to the configuration of the uv build backend" (uv changelogs). What would change the call: uv dropping or loosening its cap advice, or a usage census that shows uv_build adoption stalling.
    • A wider menu (setuptools, flit-core, pdm-backend, poetry-core and the compiled backends). Rejected, because a menu is not a pick and each extra choice has to do a job neither default nor override does for this template.
      • setuptools adds extension and legacy-setup.py use, which the template does not scaffold, and its wheel omits non-.py data files without a package-data entry.
      • flit-core does less than uv_build for this shape.
      • pdm-backend and poetry-core belong to the PDM and Poetry workflows, whose tools own the lock; that contradicts the uv pick in the landscape mapping table.
      • The compiled backends need source scaffolding (Cargo.toml, CMakeLists.txt), cache-keys, and a compiler stage in the streamlit Dockerfile.
    • Derive the uv_build bound from the running uv at render time. Rejected. It matches what uv init does, and the project template has precedent: _extensions/context.py derives the Python version from the running interpreter. The render would then depend on the machine that runs it, and the bound would split from the static Docker image tag that point 5 pairs it with.
    • Choose the default by operation, so that copier update defaults to hatchling and copy defaults to uv_build. Rejected, because Copier exposes _copier_operation only in exclude and _tasks, not in a question's default (Copier: creating a template). The before-stage migration of point 7 is the mechanism Copier documents for changing answers across versions.

    Consequences

    • The cap needs upkeep. The uv_build range and the streamlit Dockerfile tag move for every uv minor (point 5). Dependabot's uv and github-actions ecosystems update only this repository's own files, so no updater reaches a .jinja file, and the release checklist is the reminder.
    • uv_build ships git-ignored files. It does not read .gitignore: a git-ignored file inside the package directory reaches both the wheel and the sdist. hatchling honors .gitignore. Nothing the template renders today sits in that position. A project that generates files into its package tree sets source-exclude and wheel-exclude under [tool.uv.build-backend], or chooses hatchling.
    • uv_build builds from static metadata. A non-empty dynamic list fails the build with "Dynamic metadata is not supported". A project that wants a version from git tags chooses hatchling and hatch-vcs.
    • The migration is one more reason copier update needs --trust, not a new requirement. The project layer already declares _jinja_extensions, including the file-path _extensions/context.py, and _tasks, so Copier's unsafe check refuses an update of it without --trust. Versioning also lists running copier update across any declared migration as a step that refuses to start without --trust. Layers that Boilerplate bundles are copy-only (ADR-015), so only a project rendered from a git-backed project layer meets the migration.
    • The migration is the reason the change is not breaking. With it, adding build_backend is "adding a new template variable (with a sensible default)" under Versioning; without it, the change is the incompatible default change the Context describes. The migration reads and writes the answers file, which is Copier's file layout and not a Copier API, so the template version that ships it MUST pass a test that updates a hatchling project and asserts that its backend is unchanged.
    • Boilerplate's own pyproject.toml follows the same default. The repository is a pure-Python package with a static version and one src/boilerplate, the shape for which uv_build is the pick.

    Verification (2026-10-20)

    The sources below were read on 2026-10-19 and 2026-10-20, and the trials ran in scratch projects under uv 0.13.3 and Copier 9.18.1. Repository facts in the Context come from the files they name.

    • uv. Documentation: "a great choice for most Python projects", pure Python only, hatchling for build scripts, and the bound >=0.13.3,<0.14 as the example (build backend). uv init declares uv_build for plain apps since 0.12.0 (changelog 0.12.x); uv 0.13.3 writes uv_build>=0.13.3,<0.14.0 into a new project. The minor-for-breaking policy is in versioning. uv_build rejects a non-empty dynamic list in crates/uv-build-backend/src/metadata.rs (source), and a trial with uv 0.13.3 reproduced the message. The out-of-range behavior in point 6 comes from uv 0.13.3 against <0.13 (bundled copy, warning) and uv 0.12.15 against a floor above its version (index fetch).
    • File selection. In a trial with a git-ignored file inside the package and one in a generated subdirectory, uv_build shipped both and hatchling shipped neither.
    • hatchling. 1.27.0 is the first release that writes License-Expression; 1.26.3 writes Metadata 2.3 with the old License: field and no License-Expression (hatchling history; wheel inspected for both). The PyPA tutorial's hatchling >= 1.26 is therefore short of PEP 639 output by default.
    • PyPA tutorial tabs. hatchling >= 1.26, setuptools >= 77.0.3, flit_core >=3.12.0,<5, pdm-backend >= 2.4.0 (build-backend-tabs.rst).
    • setuptools. PEP 639 in the 77.0.0 notes, and PyPI lists 77.0.1 and 77.0.3 but not 77.0.0; PEP 660 in 64.0.0 (NEWS, PyPI JSON). A trial wheel omitted .txt and dotfile data that no package-data entry listed.
    • flit-core. flit_core >=3.11,<5 and PEP 639 from 3.11 (pyproject.toml docs).
    • pdm-backend. Version 2.4.0 writes License-Expression and License-File; 2.4.5 and 2.5.0 write them as well (wheels inspected). The 2.4.6 changelog entry "Add license file metadata" edits pdm-backend's own pyproject.toml and does not change the built metadata. The PDM documentation is at backend.pdm-project.org.
    • poetry-core. [project] support in 2.0.0, PEP 639 in 2.2.0, >=2.0.0,<3.0.0 in the docs, and build scripts "still considered unstable" (CHANGELOG, extension modules).
    • Compiled backends. maturin: PEP 639 in 1.9.0 and the License-Expression fix in 1.9.2 (Changelog). scikit-build-core: PEP 639 in 0.11.0 (changelog). meson-python: PEP 639 in 0.18.0 (CHANGELOG). uv init offers maturin and scikit-build-core and rejects meson-python (uv init). numpy and scipy build with meson-python, which their pyproject.toml files declare.
    • Bounds in each backend's own scaffold. hatch new writes an unbounded hatchling; flit init writes flit_core >=3.11,<5; poetry new writes a range from the installed poetry-core.
    • Render trial. A scratch copy of the project template was rendered with each choice. Each render passed validate-pyproject and ran uv lock, uv sync, pytest and uv build under uv 0.13.3. The hatchling render differs from the output of earlier template versions on the requires line only.
    • Update trial. On a toy template with a build_backend question added after the project's first render, copier update --defaults moved a hatchling project to uv_build; with the before-stage migration it stayed on hatchling, and --data build_backend=hatchling kept it as well.
    • Omitted backends. whey had four sdists in the Quansight Labs sample (PEP 517 build system popularity); py-build-cmake and enscons download figures come from pypistats, and their projects are py-build-cmake and enscons.
    • Copier. _copier_operation is documented for exclude and _tasks only (creating a template).

    Limits

    • The update trial used a toy template with the answers file .copier-answers.yml. The project template's own answers file, .copier-answers.project.yml, was not exercised, which is the reason point 7 requires an update test in the template's suite.
    • No Docker image was built. The behavior of the streamlit image under the uv:0.13 tag and the >=0.13,<0.14 range follows from the uv documentation and the 0.12.15 trial.
    • The editable and rebuild behavior of maturin, scikit-build-core and meson-python comes from their documentation; no compiler was available to run them.
    • Whether Dependabot's uv ecosystem updates a [build-system] requirement in a generated project was not tested.
    • The newest usage census (Quansight Labs, "PEP 517 build system popularity", published 2025-02-11) reports no uv_build count; it was read through its markdown source and its figures were not re-checked. The download counts in the options are monthly totals, and they serve for the order of magnitude only.

    Relationship to other ADRs

    • ADR-001 — uv's own backend and hatchling are adopted tools; Boilerplate adds only the choice between them.
    • ADR-003 and ADR-007 — the before migration of point 7 is a first-party migration, the kind that ADR-007 makes the mechanism for structural change and that ADR-003 puts on the task and extension trust surface.
    • ADR-015 — the migration edits the per-layer answers file .copier-answers.project.yml, which that ADR makes the distribution contract, and Copier's own _migrations mechanism runs it.
