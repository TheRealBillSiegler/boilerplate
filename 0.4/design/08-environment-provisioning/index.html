    Design specification

    This page is part of Boilerplate's design record: the numbered specs describe target architecture throughout, while an ADR carries its own Status line — read it to see whether the decision it records has shipped. See the Status page for what's built project-wide.

    Environment Provisioning

    Purpose

    boilerplate env apply and boilerplate env status: resolving the EnvironmentProfile extends chain, merging tool versions and packages across profile layers, generating .prototools in proto's native format, invoking proto for tool installation, and writing the .boilerplate/environment.yml provenance record.

    State Files

    A Boilerplate-managed environment contains the following state files after a successful env apply:

    File Owner Purpose
    .prototools Boilerplate (generated) / proto (runtime) Declares resolved tool versions for proto; generated by Boilerplate from the merged profile
    .protolock proto Records exact resolved tool versions and checksums; written by proto after install
    .boilerplate/environment.yml Boilerplate Records which profile was applied, the resolved extends chain, and a hash of .protolock

    Ownership invariants: - Boilerplate MUST NOT write to .protolock. That file is owned by proto. - External tools MUST NOT write to .boilerplate/environment.yml. That file is owned by Boilerplate. - .boilerplate/environment.yml MUST only be written after a fully successful provisioning operation. It MUST never reflect a partial state. - boilerplate-env.yml is the declarative input owned by the profile author. Boilerplate reads it; it MUST NOT be modified during provisioning.

    Part 1: Profile Resolution

    Purpose

    Profile resolution transforms the root EnvironmentProfile and its extends chain into a flat, ordered list of profiles and a single merged tool version map ready for .prototools generation.

    Resolution Algorithm

    Resolution takes the root profile specifier and a catalog as inputs, and produces a flat, ordered list of profiles (base-first, derived-last) as output. The algorithm performs a depth-first traversal of the extends chain, resolving each profile from the catalog.

    Inputs: Root profile specifier, profile catalog.

    Output: Ordered profile chain (base-first, derived-last; root profile always last).

    Invariants:

    • Cycle detection: A cycle in the extends chain MUST be detected and reported as BP_ENV_EXTENDS_CYCLE with the full cycle path (e.g., base -> python -> base).
    • Diamond deduplication: A profile reachable via multiple paths is included once, at the position first encountered during traversal.
    • Missing profiles: If the root profile cannot be found, fail with BP_ENV_PROFILE_NOT_FOUND. If a parent in the extends chain cannot be found, fail with BP_ENV_EXTENDS_NOT_FOUND.
    • Determinism: Given the same profile definitions, the resolved chain MUST always be identical. Traversal order is determined by the extends declaration order in each profile. This parallels the template composition tie-breaking rule in §04 Composition Engine.

    Tool Version Merging

    After the profile chain is resolved, tool versions are merged across all layers using a last-writer-wins policy: the chain is walked base-first, and each profile's tool declarations overwrite earlier values for the same tool name. The most-derived profile (last in topological order) wins for any given tool.

    This is simpler than template composition's four named merge strategies (see §04) because tool versions are simple scalars, not the complex nested structures that template configurations contain.

    The result is a flat {tool_name: version_string} map covering every tool declared in any profile in the chain.

    packages Field Merging

    After tool version merging, the packages field (map of platform key to list of PackageRequirement) is merged across the extends chain:

    • For each platform key, PackageRequirement lists are accumulated in topological order (base first, derived last).
    • When multiple profiles declare the same package (by name) for the same platform, the last-writer-wins: the most-derived profile's version constraint replaces earlier entries for that package name.
    • The result is a flat {platform: [PackageRequirement, ...]} map. Platform keys not present in a profile are inherited unchanged from ancestor profiles.
    • Tools with version constraints (e.g., >=3.10) that cannot be resolved to a single exact version MUST cause BP_ENV_VERSION_UNRESOLVABLE. Constraint-only entries are not valid for .prototools generation. Implementations SHOULD emit a descriptive error: "Profile '{name}' declares tool '{tool}' with version constraint '{constraint}' which cannot be resolved to an exact version. Declare an exact version for provisioning."

    allowed_proto_plugins Enforcement

    After tool version merging, the combined allowlist is computed by intersecting all non-empty allowed_proto_plugins lists across the chain.

    Enforcement rules: - An empty allowed_proto_plugins list on a profile means no restriction from that layer — not "block all tools." - If ALL profiles in the chain have an empty allowed_proto_plugins (the default), the combined allowlist is empty, meaning no restriction applies and all resolved tools are permitted. - If ANY profile in the chain declares a non-empty allowed_proto_plugins, the combined allowlist is the intersection of all non-empty lists across the chain. This ensures that a base profile's allowlist acts as a ceiling — derived profiles can only narrow the set, never expand it. - After computing the combined allowlist: for each tool in the resolved tool map, if the combined allowlist is non-empty and the tool name does NOT appear in the combined allowlist, raise BP_ENV_PLUGIN_NOT_ALLOWED. - Error message MUST identify the disallowed tool, the requesting profile, and the restricting profile: "Tool '{tool}' is not in the allowed_proto_plugins intersection. Requested by profile '{requesting_profile}'. Not present in allowlist defined by profile '{restricting_profile}'. Contact the platform team to update the base allowlist."

    Note (non-normative): intersection is a ceiling, not a floor — derived profiles can only narrow the allowlist, never expand it (expansion would be privilege escalation through profile composition). A tool absent from the base allowlist requires the platform team to update the base profile.

    Trust model scope: Environment profiles do not use the template trust gate (trusted/untrusted) because the security surface differs. Template tasks execute arbitrary shell commands gated by trust. Proto plugins execute in a WASM sandbox with constrained host access. The allowed_proto_plugins intersection mechanism is the security control for profiles — it provides an equivalent ceiling guarantee (base profiles restrict derived profiles) without requiring task-trust classification.

    Part 2: .prototools Generation

    Boilerplate generates proto's native configuration file (.prototools) from the merged tool version map. The generated file is written to the project root.

    Generation Rules

    • Only tools with resolved exact versions are included. Unresolvable versions MUST have already caused BP_ENV_VERSION_UNRESOLVABLE during the merge step.
    • Tool entries MUST be sorted lexicographically by name for deterministic output and clean diffs.
    • Path values MUST use forward slashes on all platforms for cross-platform compatibility.

    Ownership and Versioning

    • .prototools is a generated output owned by Boilerplate in the provisioning context; boilerplate-env.yml is the declarative input.
    • .prototools MAY be committed to version control as a development convenience -- proto reads it at runtime to determine which tool versions to activate.
    • The output is reproducible: re-running boilerplate env apply with the same profile produces an identical .prototools.
    • Entries added manually to .prototools outside of Boilerplate are not tracked and will be overwritten on the next env apply.

    Part 3: Proto Integration

    Proto Binary Discovery

    • proto MUST be discoverable via PATH.
    • boilerplate doctor MUST verify proto is installed and emit an actionable message if not found.
    • If proto is not found during env apply, the operation MUST fail immediately with BP_ENV_PROTO_NOT_FOUND before any staging or I/O occurs.

    ProtoWorker Interface

    The ProtoWorker abstracts proto's CLI behind a stable contract owned by Boilerplate. Implementations MUST isolate all proto invocations behind this interface so that proto version upgrades require changes only in the worker implementation.

    install_tool(tool_name, version, timeout) → InstallResult

    Parameter Type Description
    tool_name string Tool identifier (e.g., python, node)
    version string Exact version to install
    timeout integer Maximum seconds for this installation

    InstallResult:

    Field Type Description
    success boolean Whether installation completed
    tool_name string The tool that was installed
    version string The exact version installed
    error string or null Error message on failure

    trigger_proto_lockfile() → path

    Invokes proto's native lockfile generation (proto writes .protolock; Boilerplate does NOT) and returns the path to the resulting file. The method exists so the worker can report the lockfile path to caller code that needs to compute proto_lock_hash for the EnvironmentProvisionRecord. The worker MUST NOT itself write or modify .protolock.

    Behavioral contracts:

    • The worker MUST NOT modify .prototools — that file is generated by Boilerplate and consumed by proto.
    • If install_tool fails, the error message MUST identify the specific tool and version.
    • Proto availability MUST be verified before any installation attempt; if proto is not found, fail with BP_ENV_PROTO_NOT_FOUND.

    Invocation

    Boilerplate invokes proto to install the resolved tools. All resolved tools MUST be installed before the commit phase proceeds. Implementations SHOULD invoke proto per-tool for granular error attribution. Bulk invocation MAY be used when per-tool invocation is impractical, but the error message MUST still identify the specific tool and version that failed.

    Timeout

    Proto installation is subject to a configurable timeout, independent of the rendering timeout. Proto installation is network-bound (downloading tool binaries), so the timeout must accommodate cold-cache downloads of large toolchains.

    Failure Handling

    • If any proto install invocation fails, the provisioning MUST fail with BP_ENV_APPLY_FAILED.
    • The proto error output MUST be included in the structured log.
    • The human-readable error message MUST identify the specific tool and version that failed.

    .protolock Relationship

    proto writes .protolock to the project root after successful installation, recording exact tool versions, checksums, and platform metadata.

    Ownership boundaries: - Boilerplate MUST NOT write, modify, or delete .protolock. It is owned by proto. - Boilerplate reads .protolock after a successful install to compute the proto_lock_hash field for .boilerplate/environment.yml. - If proto did not write .protolock, proto_lock_hash is null. - boilerplate env status reads both .boilerplate/environment.yml and .protolock to report the current environment state.

    Part 3.5: Package Requirements

    Purpose

    After profile resolution and tool version merging, the merged packages map is evaluated for the current platform. This section specifies how declared PackageRequirement entries are handled during env apply and related commands.

    Platform Detection

    Boilerplate detects the current platform (Windows, WSL2, Linux, macOS) and evaluates only packages declared for that platform. Packages for other platforms are silently ignored.

    Behavior During env apply

    A declared package installs when the system-package provider kind covers it, under the trust gate ADR-009 §Trust specifies (ADR-009); Boilerplate MUST NOT invoke a package manager outside that gate, because an ungated install would violate the "orchestrate, don't replace" principle and introduce privilege escalation and safety concerns.

    For a package with no covering provider, requirements stay advisory, not automatically installed. Boilerplate validates that the package is present on the system by checking for binaries on PATH or querying the platform's package manager. Missing packages produce a WARNING with the recommended install command. Success is silent.

    Pipeline Integration

    • Plan display: When packages are declared for the current platform, the provisioning plan MUST include a Package requirements: section listing each package with the provider that installs it, or the command to install it by hand when no provider covers it. This gives the user visibility before confirming.
    • Post-install check: Covered packages install with the tools in step 4; a failed covered install raises BP_ENV_APPLY_FAILED, the same as a failed tool install: no record is written, and rerunning recovers. Uncovered packages are still checked after the installs and before the provenance record is written, and a missing one only warns. Warnings are appended to the success-path output and also surface via env status.

    env status Integration

    The env status command SHOULD check package availability for the current platform and report missing packages as warnings, using the same detection logic described above.

    Part 4: Provisioning Pipeline

    boilerplate env apply runs a single linear flow under an advisory lock. The provenance record (.boilerplate/environment.yml) is written only after a fully successful install, so it never reflects a partial state. If a step fails, the lock is released and the user re-runs env apply; because .prototools generation and proto install are idempotent, re-running converges to the resolved state.

    Flow

    1. Resolve       →  Load profile, resolve extends chain, merge tool versions, enforce allowlist
2. Plan/Confirm  →  Diff current vs. resolved; prompt for confirmation
3. Generate      →  Acquire advisory lock; write .prototools via staged write
4. Proto Install →  Invoke proto install for all resolved tools; install covered packages through their provider
5. Record Write  →  Write .boilerplate/environment.yml; release lock

    1 — Resolve

    Loads the target profile, resolves the extends chain (see §Profile Resolution), merges tool versions (last-writer-wins), and enforces the plugin allowlist. Produces a resolved tool map and ordered profile chain.

    Failures at this step (BP_ENV_PROFILE_NOT_FOUND, BP_ENV_EXTENDS_CYCLE, BP_ENV_EXTENDS_NOT_FOUND, BP_ENV_VERSION_UNRESOLVABLE, BP_ENV_PLUGIN_NOT_ALLOWED) are validation errors — no files are modified.

    2 — Plan and Confirm

    Computes the diff between the current environment state (from .boilerplate/environment.yml, if present) and the resolved tool map. Displays a provisioning plan showing installs, upgrades, and unchanged tools.

    Behavioral rules: - No differences: report "already up to date" and exit with no changes. - --dry-run: display the plan and exit without writing. - --format json without --yes or --dry-run: fail (JSON mode requires explicit intent to prevent interactive prompts in automation). - --yes or --ci: proceed without prompting. - Otherwise: prompt for confirmation (default: No). - Major version boundary crossings MUST be annotated with a warning.

    3 — Generate .prototools

    Acquires the advisory lock per 07-operational-quality.md §Concurrency Control, then writes the resolved .prototools to the project root using the staged write (temp file + rename) from the Atomic Staged Write Pattern. All subsequent steps occur under the lock.

    4 — Proto Install

    Invokes proto to install each resolved tool, subject to the timeout defined in §Proto Integration. It also installs covered packages through their provider (see §Part 3.5), with the same failure rule. Progress is reported when running interactively.

    If any installation fails, tool or covered package: the lock is released and BP_ENV_APPLY_FAILED is raised with the failing tool or package name, version, and installer output. The provenance record is not written; re-running env apply is the recovery path.

    5 — Record Write

    Computes the proto_lock_hash from .protolock (if present), writes .boilerplate/environment.yml atomically (see §.boilerplate/environment.yml Schema), and releases the advisory lock. Emits a completion summary (profile, tools installed, duration) in both human-readable and JSON output formats.

    Signal Handling

    Signal handling follows the Atomic Staged Write Pattern. The advisory lock MUST be released on cleanup. An interrupted env apply leaves no provenance record; the recovery story is to run env apply again.

    Part 5: .boilerplate/environment.yml Schema

    The .boilerplate/environment.yml schema is defined in 02-data-models.md §EnvironmentProvisionRecord. The .boilerplate/ directory is created if it does not exist. Key write invariants:

    Example

    schema_version: "boilerplate/environment@1"
boilerplate_version: "0.3.0"
profile_name: python-dev
profile_version: "1.2.0"
extends_chain:
  - base@1.0.0
  - python-dev@1.2.0
applied_at: "2026-03-20T14:30:00Z"
tools:
  node: "20.11.0"
  python: "3.12.2"
proto_lock_hash: "a3f1c9b2d8e4f7a1c3e5b7d9f2a4c6e8b0d2f4a6c8e0b2d4f6a8c0e2b4d6f8a0"

    Write Invariants

    • The file MUST be written atomically (temp file + rename).
    • The file MUST only be written after proto has successfully installed all tools (step 4 of the provisioning flow).
    • Keys MUST be sorted deterministically for clean diffs.
    • The tools map keys MUST be sorted lexicographically.

    Schema Versioning

    The schema_version field enables forward-compatible evolution. Boilerplate MUST parse any environment.yml sharing the same major version (boilerplate/environment@1). Minor version bumps add optional fields; major bumps may change semantics. When Boilerplate encounters a file with an unrecognized major version, it MUST warn and treat the file as absent rather than failing hard — the environment may still be usable even if the record cannot be interpreted.

    Part 6: Concurrency

    Environment provisioning follows the shared concurrency control pattern. See 07-operational-quality.md §Concurrency Control. The lock is acquired when .prototools is generated and released after the provenance record is written (or on failure). Network filesystem caveats apply (see 07-operational-quality.md §Platform Portability).

    Part 7: Platform-Specific Behaviors

    General platform portability rules are in 07-operational-quality.md §Platform Portability. This section covers environment-provisioning-specific platform details.

    • Windows: where file rename is not atomic, the staged write uses a copy-verify-replace pattern. Tool names in .prototools MUST be lowercase for case-insensitive filesystem compatibility.
    • WSL2: boilerplate doctor MUST detect Windows-hosted proto and warn about path mapping issues. Recommend installing proto natively within WSL2.
    • All platforms: proto MUST be on PATH.

    Part 8: env status

    boilerplate env status

    Reports the current environment state by reading .boilerplate/environment.yml and .protolock. Shows the applied profile, tools, and whether the protolock hash is consistent. Warns if no environment record exists or if the protolock hash has drifted since the last apply.

    Part 9: Error Reference

    Environment provisioning uses the BP_ENV_* error code family, plus BP_CONCURRENCY_CONTENTION and BP_FILESYSTEM_* for infrastructure failures. See 07-operational-quality.md §Phase Prefixes for the phase registry and 07-operational-quality.md §Error Message Format for the standard message format.

    Part 10: Profile Lifecycle, Drift, and Compatibility

    Profile Lifecycle Phases

    A profile passes through several phases during its useful life. Each phase produces a distinct artifact and has distinct failure modes:

    Phase Trigger Primary output Typical failures
    Authoring Author edits boilerplate-env.yml Profile draft Schema validation failure; unsatisfiable extends chain
    Publication Catalog ingest assigns immutable version Published profile Duplicate version; missing required sections
    Installation boilerplate env apply .prototools, .protolock (proto), .boilerplate/environment.yml BP_ENV_PROFILE_NOT_FOUND, BP_ENV_PLUGIN_NOT_ALLOWED, proto install failure
    Update boilerplate env apply against a newer profile version Updated state + refreshed .boilerplate/environment.yml Breaking change; lock conflict
    Removal (Future scope) Tool removal via proto Cleanup record Out of scope

    Phase events feed structured logging (per §07 Phase Vocabulary, where the relevant phase is env_apply).

    Drift

    After a profile is applied, the live environment can diverge from the recorded state — for example, a tool version drifts from .protolock, the recomputed .protolock hash no longer matches EnvironmentProvisionRecord.proto_lock_hash, a declared tool is missing, the cached profile version differs from the catalog, or the host OS/arch differs from provision time. boilerplate env status reports such drift as warnings. The remediation in every case is to re-run boilerplate env apply.

    Template-Profile Compatibility

    When a template declares requires_profile, applying or updating it verifies compatibility with the project's environment state: the required profile resolves in the catalog, the project's resolved profile name and version satisfy the template's range, and the tools the template depends on are present in the resolved profile chain. These checks are owned by the resolve/composition path (§04 Composition Engine) at new and update time. On read-only commands a mismatch is a warning surfaced via env status, not a hard failure.

    Acceptance Criteria

    Scenario Expected Outcome
    Valid single-profile apply .prototools written, proto succeeds, environment.yml written, exit 0
    Profile with extends chain Chain resolved base-first, versions merged (last-writer-wins), exit 0
    Profile not found BP_ENV_PROFILE_NOT_FOUND, no files modified, exit 3
    Cycle in extends chain BP_ENV_EXTENDS_CYCLE with full cycle path, exit 3
    Tool not in allowed_proto_plugins BP_ENV_PLUGIN_NOT_ALLOWED, no files modified, exit 3
    proto install fails BP_ENV_APPLY_FAILED, environment.yml not written, exit 1
    --dry-run Plan displayed, no files modified, exit 0
    No changes detected "Environment is already up to date.", exit 0
    Interrupted env apply No provenance record written; re-running env apply completes provisioning
    proto not installed BP_ENV_PROTO_NOT_FOUND, immediate exit 3 before any I/O
    Concurrent env apply Second invocation fails with BP_CONCURRENCY_CONTENTION after timeout

    Performance Contracts

    See §07 Operational Quality for all performance targets. Environment provisioning is I/O and network intensive; the dominant cost is proto downloading tool binaries. Boilerplate's own orchestration overhead (profile resolution, diff computation, .prototools generation) MUST be negligible relative to proto install time.
