# ADR-015: Idiomatic artifacts, orchestrated engine — a composed project is plain Copier on disk

**Status**: Accepted (target architecture; the per-layer answers-file contract is specified in [design 04](04-composition-engine.md) but not yet shipped) **Date**: 2026-07-28 **Deciders**: Project team (Bill Siegler)

> **Scope note.** This ADR names the paradigm the composition and update designs already assume, so later decisions can cite an invariant instead of re-deriving it. It changes no shipped behavior by itself; the shipped divergences it identifies are tracked in [status.md](../status.md) and the issue tracker.

## Context

The composition goal ([ADR-001](adr-001-build-vs-adopt.md)) is the experience of a singular template built from many variants. Copier's own idiom for multiple templates in one project is N independent applications, each with its own answers file, each independently updatable — and Copier's update algorithm defines "user changes" as any difference between its own pristine re-render of one template and the actual working tree, which means it has no concept of, and no need for, cross-template awareness. Two pressures meet here: being true to Copier's interfaces and idioms (so users keep every guarantee Copier gives them), and the unified experience that is the product's reason to exist (one question flow, one compose, one update). The shipped stopgap — a single canonical `.copier-answers.yml` written by Boilerplate itself — resolves that tension the wrong way: it forfeits per-layer updates and Copier's ownership of its own file.

## Decision

**A composed project MUST carry the same file set, the same file ownership, and the same update commands as a project built by running Copier N times by hand** — one measured exception, stated in point 4: each per-layer answers file additionally carries inert merged keys. *[Superseded 2026-09-30 by the [Amendment (2026-09-30)](#amendment-2026-09-30-the-update-walk-runs-through-the-merged-schema-a-layer-declares-only-what-it-owns-or-overrides): the merged keys are deliberate, because the update walk reads them.]* Idiom governs what persists; product governs what it feels like.

Composition therefore answers to two reference points at once, and each owns a different half of the result: **rendering** matches the single flattened template the layers would make if merged by hand (one question schema, one extension set, tasks running once against the finished project), while **artifact structure** matches N independent Copier applications (one answers file per layer, each independently updatable where its source is git-backed). Where a mechanism looks un-idiomatic against one reference point, check it against the other before calling it a deviation. Concretely:

1. **Artifacts are Copier's.** Each first-party template declares `_answers_file: .copier-answers.<layer>.yml` **and ships the answers-file stub** (`{{ _copier_conf.answers_file }}.jinja`) that causes Copier to write it — the directive alone is inert (the [design 04 contract](04-composition-engine.md#render-behavior)); Copier writes every answers file, and Boilerplate MUST NOT write or rewrite them. The escape hatch is a product guarantee: every **git-backed** layer of a composed project is independently `copier update`-able with vanilla Copier and no Boilerplate installed — a layer sourced from a plain directory is copy-only, per point 5. *[Superseded 2026-09-30 in its "no Boilerplate installed" clause by the [Amendment (2026-09-30)](#amendment-2026-09-30-the-update-walk-runs-through-the-merged-schema-a-layer-declares-only-what-it-owns-or-overrides): the escape hatch is a hand-run vanilla `copier update -a .copier-answers.<layer>.yml` per layer with the other layers' answers passed as data, and a child layer's derived answers make that path pause visibly on the files that render them.]*
2. **Update is orchestration of public API.** `boilerplate update` is a walk of per-layer `copier update -a .copier-answers.<layer>.yml` invocations in composition order (lower layers first, so overrides are re-asserted against an already-updated base). No Copier internals on the update path. *[Superseded 2026-09-30 by the [Amendment (2026-09-30)](#amendment-2026-09-30-the-update-walk-runs-through-the-merged-schema-a-layer-declares-only-what-it-owns-or-overrides): `boilerplate update` orchestrates Copier's `update` per layer through the merged schema, the same view compose hands each layer, and that view reaches Copier's renders through a `Worker` subclass.]* The order is recorded in a project artifact, so replaying the walk by hand does not require guessing it: `boilerplate.lock` lists `layers` in execution order ([design 02](02-data-models.md#lock-file-model)), and it is plain YAML — reading it needs no Boilerplate installed, which is what keeps the escape hatch usable. The per-layer answers files do not carry the order; they record `_src_path` and `_commit` per layer and nothing about sequence. A project with no lock — never managed by Boilerplate, or `eject`ed since — therefore has no on-disk order, and reconstructing it by hand means reading the templates' own `extends` chains.
3. **Layer stacking rides Copier's own merge model.** During any one layer's update, every other layer's contribution is user-space by construction — Copier diffs its old pristine render against the working tree, so other layers' files and overwrites are preserved when disjoint from the update and surface as ordinary three-way conflicts when they collide. Composition never needs an all-layers-at-once operation.
4. **The unified prompt experience at compose is deliberate and stays.** Prompting is ephemeral — no artifact records how questions were asked, and the rendered tree a unified compose produces is the tree N sequential Copier runs would produce from the same answers. Compose-time is therefore where the project's un-idiomatic budget is spent: the [ADR-002](adr-002-copier-internals-shim.md) shim is sanctioned there and only there. *[Superseded 2026-09-30 by the [Amendment (2026-09-30)](#amendment-2026-09-30-the-update-walk-runs-through-the-merged-schema-a-layer-declares-only-what-it-owns-or-overrides): the shim serves the update walk as well.]* One artifact-level deviation follows from the shim and is accepted rather than hidden: because every layer's Worker is handed the merged question schema, each per-layer answers file records the *full merged answer set* rather than only that layer's own questions. The extra keys are inert — at update time the layer's own `copier.yml` governs, and foreign keys are expected to drop on the first per-layer rewrite (inferred from Copier's answer-filtering behavior; not among the verified scenarios below) — so vanilla per-layer update is unaffected; the authoring rule that keeps it harmless is that a layer's files reference only answers its own `copier.yml` declares, so nothing breaks when the file self-cleans. *[Superseded 2026-09-30 by the [Amendment (2026-09-30)](#amendment-2026-09-30-the-update-walk-runs-through-the-merged-schema-a-layer-declares-only-what-it-owns-or-overrides): the merged keys are deliberate and the update walk relies on them, so they do not drop.]* That rule binds the single-owner pattern [design 04](04-composition-engine.md#managing-shared-files-across-layers) recommends for shared files, and is the stricter reading where the two could be read apart: a layer that owns a file assembled from several layers' answers MUST redeclare every question that file uses in its own `copier.yml`. Reaching those answers through `extends` is a compose-time affordance — `extends` is Boilerplate's merge, invisible to the vanilla `copier update` that the escape hatch promises — so inheritance alone does not satisfy the rule. Design 04 owns the constraint and its cost to template authors. *[Superseded 2026-09-30 by the [Amendment (2026-09-30)](#amendment-2026-09-30-the-update-walk-runs-through-the-merged-schema-a-layer-declares-only-what-it-owns-or-overrides): a layer declares its own questions and the parent questions it overrides or extends, and every other answer its files use reaches every render through the merged schema.]* The bounded fallback, should the internals coupling ever become untenable, is sequential per-layer `run_copy` with accumulated answers threaded through `data=` — shared questions still ask once, at the cost of grouped-by-layer ordering.
5. **The source model is inherited from Copier wholesale, and updateability is a per-layer property.** Remote git sources yield portable artifacts; a local git repository is a full source (tags, update) scoped to machines where the path exists, with rehoming a documented one-line `_src_path` edit; a plain directory is copy-only because Copier records no `_commit` for it — `commit: null` in the lock is the honest no-version-stream marker, not a placeholder. A mixed composition degrades per layer, not per project: `update` walks the git-backed layers and skips non-git layers with a prominent warning.

## Options considered

- **Boilerplate-owned composite answers file** (the shipped stopgap) — rejected as target: wrong author and wrong shape; it forfeits per-layer update, Copier's file ownership, and the escape hatch.
- **Boilerplate-implemented cross-layer merge or update metadata** — rejected: reimplements what Copier already provides per layer, contradicting [ADR-001](adr-001-build-vs-adopt.md).
- **Fully idiomatic compose (sequential per-layer prompting)** — rejected as the default experience: it forfeits the singular-template question flow, which is the product thesis at the moment of first contact; retained as the named fallback in point 4.
- **Idiomatic artifacts, orchestrated engine (chosen)** — the invariant above.

## Consequences

- The shipped single canonical `.copier-answers.yml` becomes a migration item; adoption already accepts the legacy singular shape beside per-layer files ([design 06](06-project-lifecycle.md)).
- The per-layer answers file becomes the distribution contract: whatever `_src_path` and `_commit` record must stay resolvable by vanilla Copier, on any machine, indefinitely. The distribution consequences are owned by [ADR-006](adr-006-template-distribution.md) as amended the same date.
- [ADR-007](adr-007-update-model.md)'s two-way degraded update for `commit: null` layers is superseded by point 5: non-git layers do not update; they are skipped with a warning, and `copier recopy` is the Copier-idiomatic refresh for such a layer when the user wants one.
- Amendments this forces in the target corpus: the non-git-layer glossary entry ([01](01-overview.md)); the `--no-base` / two-way-comparison passages ([05](05-cli-reference.md), [06](06-project-lifecycle.md)); the trust tables ([02](02-data-models.md), [03](03-template-system.md), [09](09-settings-and-configuration.md)), which name `wheel_bundle` as the trusted first-party mechanism — what replaces it depends on the open question [ADR-003](adr-003-permissive-execution.md) owns, since first-party templates arriving over the network meet ADR-003's own stated trigger for tightening; this ADR does not settle it; the `LockLayer.source_bundle` / `subdirectory` fields ([02](02-data-models.md)); INT-001's `_subdirectory` expectation; and the passages that present cross-layer question inheritance as complete without the update-time caveat point 4 attaches — the `streamlit` template description ([03](03-template-system.md)) and the shared-question-vocabulary bullet in [ADR-010](adr-010-profile.md), both of which describe a descendant reaching a base's questions through `extends`, which holds at compose and not at per-layer update. *[Superseded 2026-09-30 by the [Amendment (2026-09-30)](#amendment-2026-09-30-the-update-walk-runs-through-the-merged-schema-a-layer-declares-only-what-it-owns-or-overrides): inherited questions reach every render, compose and update, through the merged schema, and the `streamlit` description in [03](03-template-system.md) and the ADR-010 bullet say so.]*

## Verification (2026-07-28)

Empirical run against Copier 9.15.0 (Windows, git 2.55, `core.autocrlf=true`): stacked two-template fixtures (base plus an overlay overwriting a base-rendered file), per-layer answers files, vanilla `copier` CLI only — six scenarios plus an independent adversarial re-run with differently shaped fixtures.

- **Survival confirmed.** Updating the base while its diff is disjoint from the overlay's overwrite leaves the overlay's content intact and the other layer's answers file hash-identical; the updated layer's answers file advances to the new tag.
- **Collision pause confirmed.** When the base update changes a file the overlay overwrote, Copier writes inline conflict markers (`<<<<<<< before updating` / `>>>>>>> after updating`) with the overlay's content preserved on the "before" side and git reporting unmerged paths — never a silent revert, in both a line-edit and a whole-file-rewrite variant.
- **Overlay independence confirmed.** Updating the overlay layer alone lands its changes and leaves base-rendered files and the base answers file hash-identical.
- **Plain-directory degradation confirmed.** Copy from a non-git directory succeeds and records no `_commit`; `copier update` against that layer fails specifically ("Cannot update because cannot obtain old template references", exit 1) — there is no built-in two-way fallback — while the git-backed layer beside it stays fully updatable.
- **Dirty-HEAD author loop confirmed.** `--vcs-ref=HEAD` includes uncommitted template changes (with `DirtyLocalWarning`) and records a `git describe`-shaped `_commit` (`v1.0.0-1-g<hash>`); without the flag, the latest tag renders clean. That hash names the automated draft commit Copier makes inside its own throwaway clone, so it exists in no repository afterwards: a dirty-HEAD render is an authoring convenience, never a provenance record, and `new` MUST NOT use it.

Caveats the run surfaced, now part of the record:

- **The `_answers_file:` directive is inert without a stub.** Copier writes an answers file only by rendering a template-shipped `{{ _copier_conf.answers_file }}.jinja`; a template lacking one composes with exit 0 and silently produces no answers file. Design 04 names both halves of the contract, and a template offered for composition without a stub is copy-only by construction.
- **`copier update` exits 0 with unresolved conflicts in the tree**, and the updated layer's answers file already records the new tag while markers sit unresolved. Orchestration and CI must detect the pause via git unmerged state or a marker scan, never exit codes — this lands on [ADR-007](adr-007-update-model.md)'s conflict-pause envelope.
- **Byte-identity must be stated in git's content sense.** With `core.autocrlf=true`, Copier's git-based update rewrites line endings of files it otherwise leaves untouched — content-identical but raw-hash-different, and reported as modified by `git status` in most runs (one run's `git diff` suppressed it, others did not); an `autocrlf=false` control preserved exact bytes. Checksum-based drift detection must normalize line endings, and "unchanged" must never be asserted from `git status` alone.
- **Small files conflict more than edit-distance intuition suggests.** On a three-line file, a template edit and a user append at opposite ends still conflict, because the diff hunk's context spans the whole file. The pause is honest; "non-overlapping edits merge cleanly" holds only for files larger than the diff context window.
- **Compose-time ref pinning is mandatory.** Bare `copier copy` resolves the latest tag, so layer application must pin `--vcs-ref` per the resolved specifier (Boilerplate's version resolution already provides the pin).

## Verification (2026-09-04)

Empirical run against the bundled `project` and `streamlit` templates (Copier 9.18.1, Windows, git 2.55): each template copied into a local git repository and tagged; a project composed by `boilerplate new` from the wheel's plain directories, then rehomed by editing each answers file's `_src_path` to the clone and adding `_commit`; vanilla `copier update -a .copier-answers.<layer>.yml` per layer after tagging a new version of each template, in both orders.

- **Real-template defects found and fixed.** `project` declared `_exclude: [_extensions]`, which replaces Copier's default exclusions rather than extending them, so the update copied the clone's `.git` over the project's own (the engine reinstates the defaults at compose; vanilla Copier does not). `streamlit`'s files and paths used `package_name`, `project_name`, and `package_index_url` without declaring them, so its per-layer re-render produced a different Dockerfile and the update paused on a conflict no edit had caused. Both templates now restate the defaults, and `streamlit` declares the inherited questions it uses — the point 4 authoring rule, now enforced by a test over the bundled templates. *[Superseded 2026-09-30 by the [Amendment (2026-09-30)](#amendment-2026-09-30-the-update-walk-runs-through-the-merged-schema-a-layer-declares-only-what-it-owns-or-overrides): `streamlit` declares only the questions it owns or overrides, and the merged schema supplies the inherited answers its files use.]*
- **After the fixes, both layers update cleanly in either order.** The changed layer's answers file advances to the new tag, the other layer's file stays hash-identical, and new files and edits land without conflict.
- **Foreign keys drop on the first rewrite, confirmed** (inferred in the 2026-07-28 run): the project layer's answers file lost `container_registry` on its first update. *[A vanilla per-layer update; the [Amendment (2026-09-30)](#amendment-2026-09-30-the-update-walk-runs-through-the-merged-schema-a-layer-declares-only-what-it-owns-or-overrides) walk keeps them, and the hand-run hatch still trims them.]*
- **Not vanilla yet.** `project`'s `_jinja_extensions` imports a filter from the `boilerplate` package, so an update needs Boilerplate importable even though nothing orchestrates it; and `boilerplate new` cannot compose from git-backed template directories today (tracked), which is why this run rehomed the answers files by hand.

## Amendment (2026-09-30): the update walk runs through the merged schema; a layer declares only what it owns or overrides

**A layer's `copier.yml` declares its own questions and the parent questions it overrides or extends, and every other answer its files use reaches every render, at compose and at update, through the merged schema.** Composition is Boilerplate's process and not a template property: a template does not join its own `extends` chain, and the schema join specified in [design 04 §Configuration Merger](04-composition-engine.md#configuration-merger) applies to every render of every layer.

- **The invariant.** A layer's files MAY use any question of the composition's merged schema without redeclaring it. A layer MUST NOT redeclare a parent question except to override or extend it.
- **The update walk.** `boilerplate update` orchestrates Copier's `update` for each layer in lock order through the merged schema, the same view compose hands each layer. All three of Copier's renders of the layer, the old copy at the `_commit` the layer's answers file records (mirrored by `boilerplate.lock`), the in-place render and the new copy at the target, see the merged schema, and `data=` is the union of the per-layer answers files. Copier performs the three-way merge and writes the conflict markers, and Boilerplate implements no merge of its own.
- **The merged view is a property of the worker class.** Copier's `Worker._apply_update` builds its three renders (the old copy, the in-place render and the new copy) with `dataclasses.replace`, which constructs a new instance from the dataclass fields. A `Worker` subclass MUST hold the merged questions and the extension union in its fields and derive `template` from them, so every worker `replace` builds exposes the merged view; a template primed on one worker instance reaches none of the three renders ([ADR-002](adr-002-copier-internals-shim.md#amendment-2026-09-30-the-shim-serves-compose-and-update)).
- **The per-layer answers file records the full merged answer set, and the update walk reads it.** Copier's `Worker._answers_to_remember` keeps an answer only if the worker's template declares it as a question, and never keeps a hidden or secret one. A worker that exposes the merged questionnaire therefore records every merged answer in the layer's answers file, and the update walk reads the union of those files as data. Answers of `when: false` questions such as `project_slug` and `package_name` are derived: each render recomputes them and no answers file records them.
- **The escape hatch is a hand-run vanilla update, and it is not composition without Boilerplate.** A user runs `copier update -a .copier-answers.<layer>.yml` for a layer and passes the other layers' answers as data, for example `--data-file .copier-answers.project.yml`. A base layer needs nothing passed. Copier renders the old copy from the layer's own answers file and never from passed data, so a template edit on or beside a line that renders a passed-in answer conflicts on every run. A child layer's derived answers are recomputed only by the merged schema, so the hand-run path pauses on the files that render them, visibly and with conflict markers, and never loses content silently.

### Options considered

- **The merged schema held by a `Worker` subclass (chosen)** — the layer keeps its own `copier.yml` free of the join, Copier runs every render, and the view reaches all three of Copier's update renders.
- **A merged template primed on the worker instance, as compose does** — rejected: `dataclasses.replace` rebuilds the update renders without it (probed below).
- **Redeclaring inherited questions in the child layer (the 2026-09-04 state)** — superseded: it duplicates the schema by hand and contradicts the invariant.
- **A Boilerplate-shipped context hook in each layer's `_jinja_extensions` that persists inherited answers into the answers file** — rejected as the primary mechanism and kept as the runner-up: it updated cleanly in 8 updates across both orders and it also heals the hand-run hatch, but the template then ships the join mechanism, and the hook writes secret answers in clear text unless it filters them.
- **Carrying inherited answers through the child's answers-file stub with `combine`** — withdrawn: it shares the hook's objection, and a stub cannot carry derived answers for projects that never recorded them.
- **Passing data to a vanilla update with `--data-file`** — retained as the hand-run hatch with the limitation above, because the old render never sees passed data.
- **Asking `project_slug` and `package_name` as regular questions so the answers files record them** — open: it would heal the hand-run hatch for child layers at the cost of two more compose-time prompts, and the project team has not decided it.

### Verification (2026-09-30)

Empirical run against the bundled `project` and `streamlit` templates (Copier 9.18.1, Windows, local git clones, `--defaults`, `skip_tasks`): `streamlit/copier.yml` reduced to its own questions and overrides (`dependencies`, `sample_module`, `container_registry`), both layers cloned into tagged git repositories, a project composed by `boilerplate new` and rehomed to the clones with `_commit: v1` (the 2026-09-04 recipe). Each new tag edited the README line that renders `project_name` and appended a file that renders seven inherited answers, five recorded and two derived; a user line appended to the README before the first update had to survive.

- **A `Worker` subclass holding the merged view updated cleanly.** Copier's `update`, run per layer through a subclass that holds the merged questions and the extension union in fields and builds `template` from them, with `data=` the union of the per-layer answers files, exited 0 on all 8 updates in both orders (project then streamlit, streamlit then project; v2 then v3). Copier left no conflict markers, no `.rej` files and no unmerged paths, and it persisted all five inherited answers in `streamlit`'s answers file after every update. The derived values rendered (`widget_co`, `widget-co`), the package directory stayed intact and the user line survived.
- **A template primed on the worker instance lost the inherited answers.** Copier's `update`, with `worker.template` set to the merged template on the instance as compose does, exited 0 on the first `streamlit` update in both orders and dropped all five inherited answers from the answers file. The derived values rendered empty, and the second update paused with conflict markers in `README.md` and the probe file.
- **The hand-run hatch kept the user's work and paused on derived answers.** After two engine updates, `copier update -a .copier-answers.streamlit.yml --defaults --trust --data-file .copier-answers.project.yml --data package_name=widget_co --data project_slug=widget-co`, with a template edit on a far line only, exited 0 in one run, left no `.rej` file, kept the user line and the package directory, and rendered the new line. The file that renders derived answers paused with a conflict marker, because the old render cannot compute derived answers when no answers file records them, and Copier trimmed the answers file to the layer's own keys.
- **Scratch-fixture probes of vanilla updates (2026-09-29 and 2026-09-30) found three limits.** `--data` and `--data-file` rendered the new copy correctly and never reached the old copy, so a template edit on or beside a line that renders a passed-in answer conflicted every time. `_external_data` pointing at another layer's answers file worked at copy and rendered empty on update, because Copier's temporary renders lack the file. An undeclared answer left in an answers file survived one update and rendered empty on the next.

## Relationship to other ADRs

- [ADR-001](adr-001-build-vs-adopt.md) — "orchestrate, don't reimplement"; Boilerplate drives Copier's own `copy` and `update` per layer and adds one thing, the merged schema, which reaches every render through the [ADR-002](adr-002-copier-internals-shim.md) shim. Boilerplate implements no merge, update or answers-file algorithm of its own.
- [ADR-002](adr-002-copier-internals-shim.md) — the shim's charter covers compose and update: both run each layer through the merged schema, which is a property of the worker class, and the guard test reports a relocation of `Worker` or `Template` while the version pin bounds the Copier versions both paths run on.
- [ADR-006](adr-006-template-distribution.md) — distribution must satisfy the answers-file-as-contract constraints; amended accordingly.
- [ADR-007](adr-007-update-model.md) — the conflict-pause contract is how point 3's collisions surface; its non-git two-way mode is superseded by point 5.
- [ADR-013](adr-013-interactivity-contract.md) — the unified prompt flow of point 4 exists only in interactive mode; `--ci`/data-file flows bypass prompting entirely.
