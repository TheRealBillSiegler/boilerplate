# ADR-015: Idiomatic artifacts, orchestrated engine — a composed project is plain Copier on disk

**Status**: Accepted

> **Scope note.** This ADR names the paradigm the composition and update designs assume, so later decisions can cite an invariant instead of re-deriving it. For what exists in code today, see [status.md](../status.md).

## Context

The composition goal ([ADR-001](adr-001-build-vs-adopt.md)) is the experience of a singular template built from many variants. Copier's own idiom for multiple templates in one project is N independent applications, each with its own answers file, each independently updatable — and Copier's update algorithm defines "user changes" as any difference between its own pristine re-render of one template and the actual working tree, which means it has no concept of, and no need for, cross-template awareness. Two pressures meet here: being true to Copier's interfaces and idioms (so users keep every guarantee Copier gives them), and the unified experience that is the product's reason to exist (one question flow, one compose, one update). A single canonical `.copier-answers.yml` written by Boilerplate itself resolves that tension the wrong way: it forfeits per-layer updates and Copier's ownership of its own file.

## Decision

**A composed project MUST carry the same file set and the same file ownership as a project built by running Copier N times by hand, and every git-backed layer MUST stay updatable through the escape hatch of point 1, within the limits that point states** — one measured exception, stated in point 4: each per-layer answers file records its own layer's and its ancestors' answers, which the update walk reads. Idiom governs what persists; product governs what it feels like.

**Composition is Boilerplate's process, not a template property.** A template's `copier.yml` declares its own questions and the parent questions it overrides or extends, and MUST NOT declare a parent question unchanged; a template does not join its own `extends` chain. Boilerplate joins every layer's questions into the full merged schema, which the questionnaire asks once, and joins each layer with its ancestors, every layer its `extends` chain reaches, into that layer's scoped view ([design 04 §Scoped view](04-composition-engine.md#scoped-view)); it hands the scoped view to every render of the layer, at compose and at update, each render receiving the join of the versions it renders. Copier does all rendering, answers-file writing and three-way merging, and Boilerplate implements none of them.

Composition therefore answers to two reference points at once, and each owns a different half of the result: **rendering** matches, for each layer, the single flattened template that layer and its ancestors would make if merged by hand (one question schema and one extension set per layer, tasks running once against the finished project), under one questionnaire that covers the whole composition, while **artifact structure** matches N independent Copier applications (one answers file per layer, each independently updatable where its source is git-backed). Where a mechanism looks un-idiomatic against one reference point, check it against the other before calling it a deviation. Concretely:

1. **Artifacts are Copier's.** Each first-party template declares `_answers_file: .copier-answers.<layer>.yml` **and ships the answers-file stub** (`{{ _copier_conf.answers_file }}.jinja`) that causes Copier to write it — the directive alone is inert (the [design 04 contract](04-composition-engine.md#render-behavior)); Copier writes every answers file, and Boilerplate MUST NOT write or rewrite them. The escape hatch is a hand-run vanilla `copier update -a .copier-answers.<layer>.yml` for one **git-backed** layer, with its ancestors' answers passed as data, for example `--data-file .copier-answers.project.yml`; a base layer needs nothing passed, and a layer sourced from a plain directory is copy-only, per point 5. A child layer's answers file records its ancestors' answers, but a vanilla update sees only the layer's own `copier.yml`, and Copier keeps in the answers file only answers to questions the layer's template declares ([Copier: the answers file](https://copier.readthedocs.io/en/stable/configuring/#the-copier-answersyml-file)), so the first hand-run update trims the file to the layer's own keys and the passed data is what supplies the ancestors' answers from then on; an undeclared answer left in an answers file survived one update and rendered empty on the next ([Verification (2026-09-30)](#verification-2026-09-30)). The hatch updates one layer and does not compose, which bounds it twice, and it checks no recorded answer: where a target version retypes a question or tightens its validator, Copier drops an answer it reads from the layer's own answers file and records the new default with no warning. Copier renders the old copy from the layer's own answers file and never from passed data, so once the file is trimmed, a template edit on or beside a line that renders an ancestor's answer conflicts on every run. The next `boilerplate update` refills the file: the walk fills a trimmed file's keys for the old copy from the declaring layer's record, and the in-place render records the full scoped view's answers again. The stop applies only when no layer records a key, before any layer runs, naming the layer and the keys ([design 04 §Safe Update](04-composition-engine.md#safe-update)). A child layer's derived answers are recomputed only by its scoped view, so the hand-run path pauses on the files that render them, visibly and with conflict markers, and never loses content silently. A layer whose `_jinja_extensions` import from the `boilerplate` package needs that package importable in Copier's environment; the first-party templates do.
2. **Update is orchestration of Copier's update through each layer's scoped view.** `boilerplate update` runs Copier's `update` once per layer, always in composition order (lower layers first, so overrides are re-asserted against an already-updated base and a migration that renames a question rewrites the ancestor's answers file before a descendant's update reads it), and each render of that update sees the layer's scoped view at the versions it renders: the old copy of a layer renders the layer's own template at its own `_commit` and its ancestors at the versions `boilerplate.lock` records, under its scoped view joined at those versions, and the in-place render and the new copy render under its scoped view joined at the target versions, which matches Copier's own rule that the old copy renders exactly as it did. Copier performs the three-way merge, writes the conflict markers, reads each layer's own answers from that layer's answers file and prompts as it does for a vanilla update; Boilerplate passes each declaring ancestor's answers as data for the in-place render and the new copy, fills for the old copy the keys the layer's own file lacks from the declaring layer's record at the start of the walk, stops on a recorded answer the target view rejects, and runs the composition's accumulated task list once against the finished project after the walk, as at compose ([design 04 §Safe Update](04-composition-engine.md#safe-update) owns these rules; [ADR-014](adr-014-deferred-task-execution.md)). The scoped view reaches those renders through the same `Worker` subclass compose renders every layer through ([ADR-002](adr-002-copier-internals-shim.md#decision)). The order is recorded in a project artifact, so replaying the walk by hand does not require guessing it: `boilerplate.lock` lists `layers` in execution order ([design 02](02-data-models.md#lock-file-model)), and it is plain YAML, so a user replaying the walk reads the order without running Boilerplate. The per-layer answers files do not carry the order; they record `_src_path` and `_commit` per layer and nothing about sequence. A project with no lock — never managed by Boilerplate, or `eject`ed since — therefore has no on-disk order, and reconstructing it by hand means reading the templates' own `extends` chains.
3. **Layer stacking rides Copier's own merge model.** During any one layer's update, every other layer's contribution is user-space by construction — Copier diffs its old pristine render against the working tree, so other layers' files and overwrites are preserved when disjoint from the update and surface as ordinary three-way conflicts when they collide. Composition never needs an all-layers-at-once operation.
4. **The unified prompt experience at compose is deliberate and stays.** Prompting is ephemeral — no artifact records how questions were asked, and the rendered tree a unified compose produces is the tree N sequential Copier runs would produce from the same answers. The [ADR-002](adr-002-copier-internals-shim.md) shim serves compose and update alike, and one artifact-level deviation follows from it and is deliberate: because every layer's Worker exposes the layer's scoped view, each per-layer answers file records the layer's *own and its ancestors' answers* rather than only that layer's own questions, and nothing of a sibling or a descendant. Copier's `Worker._answers_to_remember` keeps an answer only if the worker's template declares it as a question, and never keeps a hidden or secret one, so a worker that exposes the scoped view records the answers to that view's questions, and the update walk reads each declaring ancestor's recorded answers from that ancestor's file and passes them as data. Compose keeps its single unified pass over the full merged schema, because nothing is recorded and no migration runs at compose. Answers of `when: false` questions such as `project_slug` and `package_name` are derived: each render recomputes them and no answers file records them. A layer's files MAY use only questions its own layer or an ancestor declares; the single-owner pattern [design 04](04-composition-engine.md#managing-shared-files-across-layers) recommends for shared files applies this to a file assembled from several layers' answers. The view stops at the ancestors because a descendant's context hook or same-named filter would otherwise change an ancestor's files, and an update step takes each question's definition and default from the full merged schema because, without it, a descendant's override of a question its ancestor adds is lost ([Verification (2026-10-06)](#verification-2026-10-06)). The bounded fallback for compose, should the internals coupling ever become untenable, is sequential per-layer `run_copy` with accumulated answers threaded through `data=` — shared questions still ask once, at the cost of grouped-by-layer ordering; for update, it is Copier's public `run_update` per layer with its ancestors' answers passed as data, with the limits of point 1.
5. **The source model is inherited from Copier wholesale, and updateability is a per-layer property.** Remote git sources yield portable artifacts; a local git repository is a full source (tags, update) scoped to machines where the path exists, with rehoming a documented one-line `_src_path` edit; a plain directory is copy-only because Copier records no `_commit` for it — `commit: null` in the lock is the honest no-version-stream marker, not a placeholder. A mixed composition degrades per layer, not per project: `update` walks the git-backed layers and skips non-git layers with a prominent warning.

## Options considered

- **Boilerplate-owned composite answers file** — rejected: wrong author and wrong shape; it forfeits per-layer update, Copier's file ownership, and the escape hatch.
- **Boilerplate-implemented cross-layer merge or update metadata** — rejected: reimplements what Copier already provides per layer, contradicting [ADR-001](adr-001-build-vs-adopt.md).
- **Fully idiomatic compose (sequential per-layer prompting)** — rejected as the default experience: it forfeits the singular-template question flow, which is the product thesis at the moment of first contact; retained as the named fallback in point 4.
- **Idiomatic artifacts, orchestrated engine (chosen)** — the invariant above.
- **The scoped view held in the fields of a `Worker` subclass (chosen)** — the layer keeps its own `copier.yml` free of the join, Copier runs every render, and the view reaches all three of Copier's update renders.
- **Every render under the full merged schema** — rejected: a descendant's context hook rewrote an ancestor's rendered files, and every answers file recorded siblings' answers ([Verification (2026-10-06)](#verification-2026-10-06)).
- **The scoped view alone as the source of question definitions and defaults at update** — rejected: an ancestor's update recorded the ancestor's own default for a new question its descendant overrides, in both walk orders ([Verification (2026-10-06)](#verification-2026-10-06)); the step takes definitions and defaults from the full merged schema instead.
- **A later layer's recorded value over an earlier one's** — rejected: passed data outranks the answers file in Copier's answer precedence (`AnswersMap.combined`), so a descendant's stale copy of an ancestor's answer, passed over the ancestor's, would shadow the value the ancestor's migration wrote.
- **One questionnaire pass before the walk** — rejected: it asks for questions a migration answers, and a renamed question's default overrode the migrated answer in both layers and both orders ([Verification (2026-10-08)](#verification-2026-10-08)).
- **A file-path extension registered once, from one source at the target versions** — rejected: the old copy renders with the new code, so the update silently keeps the old output ([Verification (2026-10-06)](#verification-2026-10-06)).
- **A merged template set on one worker instance** — rejected: `dataclasses.replace` rebuilds the update renders without it ([Verification (2026-09-30)](#verification-2026-09-30)).
- **Declaring inherited questions in each child layer so a vanilla per-layer update sees them** — rejected: it duplicates the parent's schema by hand, and the copy drifts when the parent renames or retypes the question.
- **A Boilerplate-shipped context hook in each layer's `_jinja_extensions` that persists inherited answers into the answers file** — rejected as the primary mechanism and kept as the runner-up: it updated cleanly in 8 updates across both orders and it also heals the hand-run hatch, but the template then ships the join mechanism, and the hook writes secret answers in clear text unless it filters them.
- **Carrying inherited answers through the child's answers-file stub with `combine`** — rejected: it shares the hook's objection, and a stub cannot carry derived answers for projects that never recorded them.
- **Passing data to a vanilla update with `--data-file`** — retained as the hand-run hatch with the limits in point 1, because the old render never sees passed data.
- **Asking `project_slug` and `package_name` as regular questions so the answers files record them** — open: it would heal the hand-run hatch for child layers at the cost of two more compose-time prompts, and the project team has not decided it.

## Consequences

- A project carrying a single canonical `.copier-answers.yml` is a migration item; adoption accepts the legacy singular shape beside per-layer files ([design 06](06-project-lifecycle.md)).
- The per-layer answers file is the distribution contract: whatever `_src_path` and `_commit` record must stay resolvable by vanilla Copier, on any machine, indefinitely. The distribution consequences are owned by [ADR-006](adr-006-template-distribution.md).
- Non-git layers do not update (point 5): they are skipped with a warning, and `copier recopy` is the Copier-idiomatic refresh for such a layer when the user wants one. [ADR-007](adr-007-update-model.md)'s per-layer update model follows this.
- Passages of the target corpus this decision binds: the non-git-layer glossary entry ([01](01-overview.md)); the `--no-base` / two-way-comparison passages ([05](05-cli-reference.md), [06](06-project-lifecycle.md)); the trust tables ([02](02-data-models.md), [03](03-template-system.md), [09](09-settings-and-configuration.md)), which name `wheel_bundle` as the trusted first-party mechanism — what replaces it depends on the open question [ADR-003](adr-003-permissive-execution.md) owns, since first-party templates arriving over the network meet ADR-003's own stated trigger for tightening; this ADR does not settle it; the `LockLayer.source_bundle` / `subdirectory` fields ([02](02-data-models.md)); and INT-001's `_subdirectory` expectation.

## Verification (2026-07-28)

Empirical run against Copier 9.15.0 (Windows, git 2.55, `core.autocrlf=true`): stacked two-template fixtures (base plus an overlay overwriting a base-rendered file), per-layer answers files, vanilla `copier` CLI only — six scenarios plus an independent adversarial re-run with differently shaped fixtures.

- **Survival confirmed.** Updating the base while its diff is disjoint from the overlay's overwrite leaves the overlay's content intact and the other layer's answers file hash-identical; the updated layer's answers file advances to the new tag.
- **Collision pause confirmed.** When the base update changes a file the overlay overwrote, Copier writes inline conflict markers (`<<<<<<< before updating` / `>>>>>>> after updating`) with the overlay's content preserved on the "before" side and git reporting unmerged paths — never a silent revert, in both a line-edit and a whole-file-rewrite variant.
- **Overlay independence confirmed.** Updating the overlay layer alone lands its changes and leaves base-rendered files and the base answers file hash-identical.
- **Plain-directory degradation confirmed.** Copy from a non-git directory succeeds and records no `_commit`; `copier update` against that layer fails specifically ("Cannot update because cannot obtain old template references", exit 1) — there is no built-in two-way fallback — while the git-backed layer beside it stays fully updatable.
- **Dirty-HEAD author loop confirmed.** `--vcs-ref=HEAD` includes uncommitted template changes (with `DirtyLocalWarning`) and records a `git describe`-shaped `_commit` (`v1.0.0-1-g<hash>`); without the flag, the latest tag renders clean. That hash names the automated draft commit Copier makes inside its own throwaway clone, so it exists in no repository afterwards: a dirty-HEAD render is an authoring convenience, never a provenance record, and `new` MUST NOT use it.

Caveats the run surfaced, now part of the record:

- **The `_answers_file:` directive is inert without a stub.** Copier writes an answers file only by rendering a template-shipped `{{ _copier_conf.answers_file }}.jinja`; a template lacking one composes with exit 0 and silently produces no answers file. Design 04 names both halves of the contract, and a template offered for composition without a stub is copy-only by construction.
- **`copier update` exits 0 with unresolved conflicts in the tree**, and the updated layer's answers file already records the new tag while markers sit unresolved. Orchestration and CI must detect the pause via git unmerged state or a marker scan, never exit codes — this lands on [ADR-007](adr-007-update-model.md)'s conflict-pause envelope.
- **Byte-identity must be stated in git's content sense.** With `core.autocrlf=true`, Copier's git-based update rewrites line endings of files it otherwise leaves untouched — content-identical but raw-hash-different, and reported as modified by `git status` in most runs (one run's `git diff` suppressed it, others did not); an `autocrlf=false` control preserved exact bytes. Checksum-based drift detection must normalize line endings, and "unchanged" must never be asserted from `git status` alone.
- **Small files conflict more than edit-distance intuition suggests.** On a three-line file, a template edit and a user append at opposite ends still conflict, because the diff hunk's context spans the whole file. The pause is honest; "non-overlapping edits merge cleanly" holds only for files larger than the diff context window.
- **Compose-time ref pinning is mandatory.** Bare `copier copy` resolves the latest tag, so layer application must pin `--vcs-ref` per the resolved specifier (Boilerplate's version resolution already provides the pin).

## Verification (2026-09-04)

Empirical run against the bundled `project` and `streamlit` templates (Copier 9.18.1, Windows, git 2.55): each template copied into a local git repository and tagged; a project composed by `boilerplate new` from the wheel's plain directories, then rehomed by editing each answers file's `_src_path` to the clone and adding `_commit`; vanilla `copier update -a .copier-answers.<layer>.yml` per layer after tagging a new version of each template, in both orders.

- **Real-template defects found.** `project` declared `_exclude: [_extensions]`, which replaces Copier's default exclusions rather than extending them, so the update copied the clone's `.git` over the project's own (the engine reinstates the defaults at compose; vanilla Copier does not). `streamlit`'s files and paths used `package_name`, `project_name`, and `package_index_url` without declaring them, so its vanilla per-layer re-render, which sees only the layer's own `copier.yml`, produced a different Dockerfile and the update paused on a conflict no edit had caused. For the rest of the run, `project` restated the default exclusions and `streamlit` declared those questions.
- **With those fixes, both layers updated cleanly in either order.** The changed layer's answers file advanced to the new tag, the other layer's file stayed hash-identical, and new files and edits landed without conflict.
- **A vanilla per-layer update drops foreign keys on its first rewrite.** The project layer's answers file lost `container_registry` on its first update.
- **The vanilla update needed Boilerplate importable.** `project`'s `_jinja_extensions` imports a filter from the `boilerplate` package. `boilerplate new` could not compose from git-backed template directories at the time of the run, which is why the run rehomed the answers files by hand.

## Verification (2026-09-30)

Empirical run against the bundled `project` and `streamlit` templates (Copier 9.18.1, Windows, local git clones, `--defaults`, `skip_tasks`): `streamlit/copier.yml` reduced to its own questions and overrides (`dependencies`, `sample_module`, `container_registry`), both layers cloned into tagged git repositories, a project composed by `boilerplate new` and rehomed to the clones with `_commit: v1` (the 2026-09-04 recipe). Each new tag edited the README line that renders `project_name` and appended a file that renders seven inherited answers, five recorded and two derived; a user line appended to the README before the first update had to survive.

- **A `Worker` subclass holding the merged view updated cleanly.** Copier's `update`, run per layer through a subclass that holds the merged questions and the extension union in fields and builds `template` from them, with `data=` the union of the per-layer answers files (the merge order of the union was not recorded), exited 0 on all 8 updates in both orders (project then streamlit, streamlit then project; v2 then v3). Copier left no conflict markers, no `.rej` files and no unmerged paths, and it persisted all five inherited answers in `streamlit`'s answers file after every update. The derived values rendered (`widget_co`, `widget-co`), the package directory stayed intact and the user line survived.
- **A template set on the worker instance lost the inherited answers.** Copier's `update`, with `worker.template` set to the merged template on one instance, exited 0 on the first `streamlit` update in both orders and dropped all five inherited answers from the answers file. The derived values rendered empty, and the second update paused with conflict markers in `README.md` and the probe file.
- **The hand-run hatch kept the user's work and paused on derived answers.** After two engine updates, `copier update -a .copier-answers.streamlit.yml --defaults --trust --data-file .copier-answers.project.yml --data package_name=widget_co --data project_slug=widget-co`, with a template edit on a far line only, exited 0 in one run, left no `.rej` file, kept the user line and the package directory, and rendered the new line. The file that renders derived answers paused with a conflict marker, because the old render cannot compute derived answers when no answers file records them, and Copier trimmed the answers file to the layer's own keys.
- **Scratch-fixture probes of vanilla updates (2026-09-29 and 2026-09-30) found three limits.** `--data` and `--data-file` rendered the new copy correctly and never reached the old copy, so a template edit on or beside a line that renders a passed-in answer conflicted every time. `_external_data` pointing at another layer's answers file worked at copy and rendered empty on update, because Copier's temporary renders lack the file. An undeclared answer left in an answers file survived one update and rendered empty on the next.

## Verification (2026-10-06)

Empirical run against the bundled `project` and `streamlit` templates and synthetic layers (Copier 9.18.1, Windows, git 2.55): one tagged git repository per layer, every view built by Boilerplate's own Resolver and Composer, and every compose and update run through a `Worker` subclass holding one view per ref, in lock order and in reverse. Every view joined the layer and its ancestors at one shared ref name per step; a view joining independently versioned ancestors was not exercised, and neither was a step whose ancestor moved while the layer's own version did not, the case in which the old copy, the new copy and the in-place render carry one ref and the recorded-versions and target-versions views differ.

- **The full merged schema let a descendant change an ancestor's files.** A `streamlit` context hook that overwrote `description` rewrote `project`'s `pyproject.toml` and package `__init__.py` to the hook's value when every layer rendered under the full merged schema, and `project`'s answers file recorded `streamlit`'s `container_registry`. Under the scoped view, `project` rendered the answered `description` and recorded only its own questions.
- **Each answers file recorded exactly its scoped view.** In a diamond (`docs` extends `project`; `app` extends `streamlit` and `docs`), each answers file recorded its own and its ancestors' questions and no other, and the updates of `docs` and `app` left no conflict markers, no `.rej` files and no unmerged paths. A three-layer chain (`project`, `streamlit`, and a layer extending `streamlit`) updated cleanly in both orders.
- **The questionnaire pass carried a descendant's override of a new ancestor question.** When `project` added `license` (default `MIT`) and `streamlit` overrode its default to `Apache-2.0`, the scoped view with no pass rendered and recorded `MIT` in `project` in both orders, with no error. With one non-interactive pass over the full merged schema at the target versions before the walk, the file and both answers files held `Apache-2.0` in both orders.
- **A file-path extension declared by an ancestor needed registration per layer and ref.** A `streamlit` file using a filter that `project` declares as a file path failed to render with no registration (`No filter named 'probe_shout'`). Registered per layer and ref from `project`'s source at each ref, the update moved the file from the old ref's output to the new ref's with no conflict markers; registered once from one source at the target ref, the old copy rendered with the new code, the old and new copies matched, and the file silently kept the old ref's output with no error. A `streamlit` context hook never reached `project`'s files, at compose or at any update.
- **Copier's update replaced a rejected recorded answer silently.** `project` v2 retyped `port` from `str` to `int`, dropped `GPL-3.0` from a `license` choice list, or added a validator the recorded `author_email` failed. With the recorded answers passed as data, the in-place render's questionnaire raised a `ValueError` before it wrote any file and left the tree and the answers files untouched, while a castable value (`"8080"`) carried over as `8080`. With no data passed, Copier dropped the recorded answer and recorded the new default (`8080`, `MIT`, a valid default address), exited cleanly and printed no warning; a new default that also failed the validator failed the update.
- **Copier ran a layer's tasks three times per update.** With a marker task in `project` and in `streamlit`, compose ran each task once in the destination. A Copier update with tasks enabled ran the updated layer's own task three times, in the old-copy temporary directory, in place and in the new-copy temporary directory, and never ran the other layer's task.
- **Only ancestors-first order carried a renamed question.** `project` v2 renamed `author_name` to `maintainer_name` and shipped a before-stage migration that rewrote the key in its own answers file. In lock order the value carried over in both layers. In reverse order, with the migration in `project` alone, `streamlit`'s update found neither name, recorded the template default `Your Name` with no error or conflict, and kept it after `project`'s later update; with the same migration in `streamlit` too, both orders carried the value.

## Verification (2026-10-08)

Probe scenarios against Copier 9.18.1, on the bundled `project` and `streamlit` templates.

- **A questionnaire pass run before the walk forced a renamed question's default over the migrated answer.** `project` v2 renamed `author_name` to `maintainer_name` behind a before-migration. The pass ran before that migration, found `maintainer_name` unanswered, and its forced default `Your Name` replaced the migrated value in both layers and both orders.

## Relationship to other ADRs

- [ADR-001](adr-001-build-vs-adopt.md) — "orchestrate, don't reimplement"; Boilerplate drives Copier's own `copy` and `update` per layer and adds one thing, the join: the full merged schema the questionnaire asks, and each layer's scoped view, which reaches every render of that layer through the [ADR-002](adr-002-copier-internals-shim.md) shim. Boilerplate implements no merge, update or answers-file algorithm of its own.
- [ADR-002](adr-002-copier-internals-shim.md) — the shim's charter covers compose and update: both run each layer through its scoped view, which is a property of the worker class, and the guard test reports a relocation of `Worker` or `Template` while the version pin bounds the Copier versions both paths run on.
- [ADR-006](adr-006-template-distribution.md) — distribution must satisfy the answers-file-as-contract constraints.
- [ADR-007](adr-007-update-model.md) — the conflict-pause contract is how point 3's collisions surface, and its per-layer update skips non-git layers per point 5.
- [ADR-013](adr-013-interactivity-contract.md) — the unified prompt flow of point 4 exists only in interactive mode; `--ci`/data-file flows bypass prompting entirely.
